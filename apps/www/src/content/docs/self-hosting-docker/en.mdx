If you'd rather not use Cloudflare at all, Synch's server also runs as a plain Node.js process. This guide covers running it on your own hardware - a homelab NAS, a small VPS, an Incus/LXC container, anywhere you can run a long-lived process and expose a port - with either [Docker Compose](#deploy-with-docker-compose) or [systemd](#run-without-docker-systemd).

Data is stored entirely on disk: one SQLite file per vault, plus a small app database for accounts and vault metadata. There's no D1, no Durable Objects, no R2 - just files in a directory you control.

If you'd rather deploy to a free Cloudflare account instead, see the [Cloudflare self-hosting guide](/self-hosting/).

## Before you deploy

Either way, you'll need a way to reach the server from your Obsidian devices - either on your local network, or over the internet if you want to sync away from home (put it behind a reverse proxy with TLS in that case; the server itself only speaks plain HTTP).

## Deploy with Docker Compose

You'll need Docker and Docker Compose installed.

1. Clone the repository and go to the API directory:

   ```bash
   git clone https://github.com/hjinco/synch.git
   cd synch/apps/api
   ```

2. Copy the example environment file:

   ```bash
   cp .env.example .env
   ```

3. Edit `.env` and fill in:
   - `PUBLIC_URL` - the address clients will reach this server at (e.g. `http://192.168.1.50:8787` on your LAN, or `https://synch.your-domain.example` behind a reverse proxy). This must match exactly, including scheme and port - it's used to validate incoming request origins.
   - `BETTER_AUTH_SECRET` and `SYNC_TOKEN_SECRET` - two independent random secrets. Generate each with:

     ```bash
     openssl rand -hex 32
     ```
   - `AUTH_ALLOWED_EMAILS` (required, unless you disable password sign-in entirely - see [Single sign-on (OIDC)](#single-sign-on-oidc) below) - a comma-separated list of the exact email addresses allowed to create accounts:

     ```text
     AUTH_ALLOWED_EMAILS=you@example.com,family@example.com
     ```

     Matching ignores letter case and surrounding spaces. This setting only controls new accounts, so existing users can still sign in after their address is removed from the list.
   - `OIDC_DISCOVERY_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` (optional) - enable single sign-on. See [Single sign-on (OIDC)](#single-sign-on-oidc) below.

4. Start the server:

   ```bash
   docker compose up -d
   ```

Vault and blob data persist in the `synch-data` Docker volume across restarts and upgrades. To move to a new host, copy that volume along with your `.env` file.

### Blob storage

By default, encrypted file contents are stored on disk inside the same data volume. If you'd rather use an S3-compatible bucket (AWS S3, MinIO, R2, etc.), uncomment and fill in the `BLOB_STORAGE=s3` block in `.env` before starting the container.

### Single sign-on (OIDC)

Synch can authenticate through any standards-compliant OpenID Connect provider - Keycloak, Authentik, Authelia, Zitadel, Dex, Okta, Entra ID, Auth0, and others all work. This isn't tied to one vendor.

Uncomment and fill in these three in `.env`:

- `OIDC_DISCOVERY_URL` - your provider's discovery document, typically ending in `/.well-known/openid-configuration`
- `OIDC_CLIENT_ID`
- `OIDC_CLIENT_SECRET`

These three belong together: fill in all of them, or leave all of them commented out. Setting only one or two is treated as a broken configuration, not a disabled feature - the server refuses to start until the missing value is filled in, rather than quietly running without OIDC. Keep `OIDC_CLIENT_SECRET` in `.env`, which is not committed to version control, and never move it into a file that is.

Whatever provider you use, register this exact redirect URI with it:

```text
{PUBLIC_URL}/api/auth/callback/oidc
```

using the `PUBLIC_URL` you set above - for example `https://synch.your-domain.example/api/auth/callback/oidc`. Getting this path wrong is the single most common way to lose an hour on OIDC setup; most providers call it a "redirect URI" or "callback URL" on their own client configuration screen.

Optional variables, also in `.env`:

- `OIDC_PROVIDER_NAME` - label shown on the sign-in button. Defaults to `Single sign-on`.
- `OIDC_SCOPES` - comma-separated scopes to request. Defaults to `openid,profile,email`.
- `OIDC_ACCOUNT_ISSUER` - overrides the issuer identity used to scope linked accounts. Defaults to the origin of `OIDC_DISCOVERY_URL`; only set this if your provider's issuer differs from that origin.

#### Account linking by email

When someone signs in through OIDC, Synch links that session to any existing local account with the same email address instead of creating a duplicate. This is deliberate: someone who registered with a password before OIDC was set up keeps their existing vaults after switching to single sign-on. Your provider must mark the address as verified (the `email_verified` claim in the ID token); Synch rejects OIDC sign-ins whose email the provider hasn't verified, the same as for Google and GitHub sign-in.

One consequence is worth knowing before you rely on this. Self-hosted Synch doesn't send verification emails, so registering an address here never proves control of it - and that's true regardless of whether your provider verifies addresses on its own side. So if password sign-up is still open, anyone could register one of your allowed addresses before its real owner ever signs in through your provider - and would then be linked to that account the moment the real owner does. Vault contents stay safe either way, since they're encrypted on the client with a passphrase the server never sees; what's exposed in that scenario is a session, the vault list and its metadata, the encrypted blobs, and the ability to delete or purge vaults - not the notes themselves. This is also why reusing your account password as your vault passphrase isn't a good idea: it collapses a separation the encryption is designed to preserve.

Setting `AUTH_EMAIL_PASSWORD=disabled` (see below) closes this off, since no password account - and so no address to register ahead of its owner - can be created.

#### Turning off password sign-in

Password sign-up stays enabled by default alongside OIDC. Once you've confirmed OIDC sign-in works, you can require it exclusively by setting `AUTH_EMAIL_PASSWORD=disabled` in `.env` and restarting the service. At that point `AUTH_ALLOWED_EMAILS` stops being read, since there's no password sign-up left for it to gate.

#### If your provider is unreachable

While your OIDC provider's discovery endpoint can't be reached, sign-in through it fails, and so does any request that needs to check a live session. Whether an in-flight sync keeps working depends on how recently its sync token was issued - those tokens are short-lived, so anything already close to expiry re-checks the session and fails along with sign-in.

There's also no way to bound how long Synch will wait on a provider that's reachable but slow - that fetch happens inside the auth library with no timeout available to configure. A provider that hangs is worse than one that refuses the connection, since a refusal fails fast and a hang doesn't. If you can choose between providers or instances, prefer the one that fails fast.

### Upgrading

```bash
git pull
docker compose up -d --build
```

Database migrations run automatically on startup.

## Run without Docker (systemd)

The server runs as a prebuilt Node.js artifact (`dist/server.mjs`) - Docker is a convenience, not a requirement. This is a reasonable choice if you're already running a VM (an Incus/LXC container, for example) and would rather not add Docker as a dependency.

On Debian/Ubuntu, [`install.sh`](https://github.com/hjinco/synch/blob/main/apps/api/install.sh) automates everything below - clone the repo, then `cd apps/api && sudo ./install.sh`. It's safe to re-run (e.g. after `git pull`) to update and restart. The manual steps:

1. Install Node.js 24 and a build toolchain (needed for `better-sqlite3`'s native module if no prebuilt binary matches your VM's architecture/libc):

   ```bash
   # Debian/Ubuntu
   sudo apt install -y nodejs python3 make g++
   sudo corepack enable
   ```

2. Clone the repository, build the Node artifact, and retain only production dependencies:

   ```bash
   git clone https://github.com/hjinco/synch.git /opt/synch
   cd /opt/synch/apps/api
   pnpm install --frozen-lockfile --filter @synch/api...
   pnpm build:node
   pnpm install --frozen-lockfile --filter @synch/api... --prod --offline
   ```

3. Copy `.env.example` to `.env` and fill it in exactly as in the Docker Compose steps above.

4. Install and start the [example systemd unit](https://github.com/hjinco/synch/blob/main/apps/api/synch-api.service.example):

   ```bash
   sudo useradd --system --home /var/lib/synch-api --create-home synch
   sudo cp synch-api.service.example /etc/systemd/system/synch-api.service
   # edit the unit's paths/User/Group if you didn't use /opt/synch or the synch user
   sudo systemctl daemon-reload
   sudo systemctl enable --now synch-api
   ```

5. Check it's up:

   ```bash
   curl http://localhost:8787/health
   sudo journalctl -u synch-api -f
   ```

### Upgrading (systemd)

```bash
cd /opt/synch
git pull
cd apps/api
pnpm install --frozen-lockfile --filter @synch/api...
pnpm build:node
pnpm install --frozen-lockfile --filter @synch/api... --prod --offline
sudo systemctl restart synch-api
```

### Binding to localhost only

By default the server listens on `0.0.0.0` (all interfaces) - Docker Compose needs this to make its port publishing work. If you're running the systemd deployment behind a local reverse proxy (e.g. [`tailscale serve`](https://tailscale.com/kb/1242/tailscale-serve), nginx, Caddy) and don't want the server directly reachable on your LAN or public interface, set `HOST=127.0.0.1` in `.env`. The example systemd unit (and `install.sh`) already does this for you.

After changing it, update `PUBLIC_URL` to the address clients will actually connect through (your reverse proxy's address, not `127.0.0.1`) and restart the service - `PUBLIC_URL` is what better-auth validates incoming request origins against.

## Connect Obsidian

1. Open Obsidian.
2. Go to **Settings**.
3. Open **Synch**.
4. In **Self-hosted server**, paste your server's `PUBLIC_URL`. Do not include a trailing `/`.
5. Click **Save**.
6. Continue sign-in and vault setup normally.
